# Queris: Evaluated Text-to-SQL Analytics Agent

## Current status

✅ **Phase 8 demo UX is complete and awaiting review.** Queris now includes a local Streamlit flow from a natural-language question through validated read-only SQL to a results table, automatic chart, and plain-language explanation. Successful and blocked attempts remain auditable in session history with live-schema sources, retry count, total latency, and blocked status. The versioned five-question live demo evaluation passed 5/5 with `gemini-3.5-flash`. The completed Phase 7 suite remains a permanent part of the full evaluation harness with 27 adversarial cases and independent criteria. No API exists yet. See the [`roadmap.md`](roadmap.md#current-focus) for the exact resume point.

## Product vision

A Text-to-SQL agent that answers natural-language questions over analytics data (e.g. *"Which categories lost margin last quarter, and in which regions?"*), running a controlled, auditable flow:

1. Inspects the available schema.
2. Enriches ambiguous identifiers with reviewed business metadata.
3. Semantically retrieves the relevant tables/columns (embeddings + cosine similarity).
4. Generates SQL.
5. Validates that the query is read-only.
6. Executes it on DuckDB.
7. Automatically fixes syntax errors (think-act-observe loop).
8. Shows results, a visualization, and an explanation.
9. Saves the query and the sources used.

The differentiator versus an "API-calling chatbot" is the **evaluation layer**: a set of 50–100 questions with expected SQL, measuring execution accuracy, result accuracy, blocked-unsafe-query rate, average number of retries, latency, and cost — plus adversarial tests (DROP TABLE attempts, prompt injection inside text fields, ambiguous questions, similarly-named columns, unanswerable questions).

## Security boundaries

- **Mandatory read-only mode**: no query generated by the agent may execute `INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `CREATE`, or any write DDL/DML. This is enforced with SQLGlot (parsing + statement whitelist) before execution on DuckDB — not via prompting alone.
- **Prompt injection**: any text coming from data (cell values, semantic search results, etc.) is treated as untrusted data, never as an instruction.
- **No system command execution** from the agent's tools; the agent may only call explicitly exposed functions (schema lookup, vector search, validated SQL execution).
- **Traceability**: every executed query and its sources (tables/columns used) must be logged so they can be audited against the evaluation set.

These constraints apply to the first implementation and cannot be deferred to a later phase.

## Retrieval evaluation

The versioned wide-schema evaluation uses a deterministic offline token-hash embedder so tests do
not depend on credentials, network access, or provider model changes. At `k=5`, the 10 reviewed
question-to-column labels produce these macro metrics:

| Schema documents | Precision@5 | Recall@5 |
|---|---:|---:|
| Raw identifiers | 0.14 | 0.70 |
| Reviewed enrichment | 0.20 | 1.00 |

The enriched documents recover all three relevant columns missed by raw identifiers. Reproduce the
comparison after creating the wide fixture:

```bash
queris-retrieval-eval data/wide.duckdb metadata/wide-schema.v1.yaml \
  evals/wide_schema_retrieval.json --top-k 5
```

## Phase 6 evaluation

Export `GEMINI_API_KEY`, create the trusted retail and wide-schema fixtures separately, and then run
the full read-only evaluation with:

```bash
queris-sample-data data/retail.duckdb
queris-wide-data data/wide.duckdb
queris-evaluation-report data/retail.duckdb
```

The command prints the current metric table plus independent adversarial pass criteria and a
compatible prior-run comparison. It writes the latest full report to `evals/results/phase6.json`
and appends a timestamped report under `evals/results/phase6-history/`. Both locations are ignored
local audit artifacts. Pass both `--input-usd-per-million` and `--output-usd-per-million` to include
an explicit-rate cost estimate.

## Streamlit demo

Export `GEMINI_API_KEY`, create the retail fixture, and launch the local demo:

```bash
queris-sample-data data/retail.duckdb
queris-demo
```

Enter the DuckDB path in the sidebar and ask an analytics question. Successful queries show the
validated SQL, result rows, a chart when at least one numeric field is available, and a concise
explanation. The session history retains each successful question, SQL statement, and referenced
live-schema tables and columns, as well as terminal blocked attempts. The current result and history
show retry count, total latency, and whether validation blocked the final SQL before execution. The
agent continues to execute through the same read-only validation and retry loop used by the
evaluation harness.

Run the strict five-question live demo exit evaluation with:

```bash
queris-demo-eval data/retail.duckdb
```

The ignored local report records the generated SQL, result correctness, explanation, retries,
latency, blocked state, and any failure details for each reviewed demo question.
